## 2. Categorized List of ALL Errors Found with Severity Levels

### CRITICAL (Will cause compilation failure)

#### ERROR #1: iOS FirebaseManager Signature Mismatch
- **Location**: `composeApp/src/iosMain/kotlin/bo/bordadoxdanny/app/firebase/FirebaseManager.ios.kt`
- **Error Type**: Compilation
- **Root Cause**: The `actual` implementation does not match the `expect` class declaration. The expect class in `commonMain` declares:
  ```kotlin
  suspend fun <T : Any> getData(path: String, clazz: KClass<T>): Result<T?>
  fun <T : Any> observeData(path: String, clazz: KClass<T>): Flow<T?>
  ```
  But the iOS actual only implements:
  ```kotlin
  actual suspend fun getData(path: String): Result<Any?>  // Missing generic, missing clazz param
  ```
  And is completely missing `observeData`.
- **Fix Applied**: Update the iOS actual class to match expect signatures exactly:
  ```kotlin
  actual suspend fun <T : Any> getData(path: String, clazz: KClass<T>): Result<T?> {
      TODO("Not yet implemented")
  }
  
  actual fun <T : Any> observeData(path: String, clazz: KClass<T>): Flow<T?> {
      TODO("Not yet implemented")
  }
  ```
- **Verification**: Run `./gradlew :composeApp:compileKotlinIosArm64` to verify iOS compilation succeeds.

#### ERROR #2: Duplicate Worker Package Classes
- **Location**: `composeApp/src/androidMain/kotlin/bo/bordadoxdanny/app/worker/LogUploadWorker.kt` and `composeApp/src/androidMain/kotlin/bo/bordadoxdanny/app/worker/LogScheduler.kt`
- **Error Type**: Compilation / Logic
- **Root Cause**: Two separate packages exist with the same class names:
  - `bo.bordadoxdanny.app.worker.LogUploadWorker` (old version, no Koin injection)
  - `bo.bordadoxdanny.app.workers.LogUploadWorker` (active version, Koin-injected)
  
  The `AndroidModule.kt` imports and registers `bo.bordadoxdanny.app.workers.LogUploadWorker` via `workerOf(::LogUploadWorker)`. The duplicate in `worker/` package is dead code that will never be used but exists in the same source set, causing confusion and potential import mistakes. The `worker/LogUploadWorker.kt` uses `KoinComponent` and `inject()` while the `workers/LogUploadWorker.kt` uses constructor injection via Koin worker DSL.
- **Fix Applied**: Delete the duplicate `worker/` package directory entirely (both files). The active versions are already in `workers/` and properly registered in Koin.
- **Verification**: Run `./gradlew :composeApp:compileKotlinAndroid` to verify no compilation errors and that Koin worker DSL resolves correctly.

### HIGH (Will cause runtime failures)

#### ERROR #3: MyFirebaseMessagingService Not Registered in AndroidManifest
- **Location**: `composeApp/src/androidMain/AndroidManifest.xml` and `composeApp/src/androidMain/kotlin/bo/bordadoxdanny/app/MyFirebaseMessagingService.kt`
- **Error Type**: Logic / Runtime
- **Root Cause**: Two FCM services exist:
  - `MyFcmService` — registered in manifest, handles FCM messages
  - `MyFirebaseMessagingService` — NOT registered in manifest, but contains `onNewToken()` override that saves FCM token to Firebase Database. Without manifest registration, `onNewToken()` will never be called, so FCM token refresh events will be lost.
- **Fix Applied**: Register `MyFirebaseMessagingService` in AndroidManifest.xml with `<service android:name=".MyFirebaseMessagingService" android:exported="false">` and intent-filter for `com.google.firebase.MESSAGING_EVENT`. Since both services handle the same intent, we should merge the best behavior or explicitly decide. Actually, having two services for the same intent is problematic — the system may only deliver to one. Better approach: move the `onNewToken` logic from `MyFirebaseMessagingService` into `MyFcmService` (which is already registered), then delete `MyFirebaseMessagingService`.
  - Move `onNewToken()` body from `MyFirebaseMessagingService` to `MyFcmService`
  - Delete `MyFirebaseMessagingService.kt`
- **Verification**: Verify manifest has exactly one FCM service (`MyFcmService`), and test FCM token refresh triggers local DB update.

#### ERROR #4: Duplicate LogScheduler Package (same as #2 but for the scheduler)
- **Location**: `composeApp/src/androidMain/kotlin/bo/bordadoxdanny/app/worker/LogScheduler.kt`
- **Error Type**: Logic
- **Root Cause**: Same as ERROR #2 — `bo.bordadoxdanny.app.worker.LogScheduler` is dead code. The active implementation is `bo.bordadoxdanny.app.workers.LogScheduler` which implements the `WorkerScheduler` interface and is bound in Koin. The `worker/LogScheduler.kt` doesn't implement the interface and has different method names.
- **Fix Applied**: Delete the `worker/` package directory (both `LogUploadWorker.kt` and `LogScheduler.kt`).
- **Verification**: Ensure `BordadosApplication.kt` still resolves `get<LogScheduler>()` from the `workers` package.

### MEDIUM (Potential runtime issues)

#### ERROR #5: iOS getDatabaseBuilder Has Suppressed Reference Error
- **Location**: `composeApp/src/iosMain/kotlin/bo/bordadoxdanny/app/data/database/getDatabaseBuilder.kt`
- **Error Type**: Runtime
- **Root Cause**: Line 12 uses `@Suppress("UNRESOLVED_REFERENCE")` for `AppDatabaseConstructor.initialize()`. This suggests KSP may not be generating the `AppDatabaseConstructor` for the iOS target correctly. On iOS, Room with KSP requires proper code generation. If the constructor isn't generated, the app will crash at runtime with `NoClassDefFoundError` or similar.
- **Fix Applied**: Verify KSP generates Room constructors for iOS. Add explicit KSP configuration if needed. The suppresion should be removed once verified. For now, add a note that this needs KSP room compiler setup verification for iOS.
- **Verification**: Run `./gradlew :composeApp:compileKotlinIosSimulatorArm64` and inspect generated code in build directories.

#### ERROR #6: Core Daemon Module Missing iOS Actual Implementations
- **Location**: `core/daemon/src/commonMain/kotlin/` — expect declarations for `NotificationHelper`, `HeartbeatScheduler`, `WatchdogService` and `expect fun createDaemonDatabase` only have Android actuals.
- **Error Type**: Compilation (for iOS target)
- **Root Cause**: The daemon module's `core/daemon/src/commonMain/kotlin/` declares expect/actual patterns but only provides Android actual implementations. If the daemon module is ever compiled for iOS, it will fail. Currently, the `composeApp` module only uses daemon on Android (via `BordadosApplication`), but the module itself declares iOS targets in build.gradle.
- **Fix Applied**: Either:
  a) Add iOS actual implementations (stubs/no-ops) for daemon expect declarations, OR
  b) Remove iOS targets from `core/daemon/build.gradle.kts` if daemon is Android-only.
  - **Decision**: Option (b) is cleaner. Daemon uses `android.content.Context`, `Settings.Secure`, `NotificationManager`, WorkManager, etc. — all Android-only. Remove iOS targets from core/daemon.
- **Verification**: Verify `core/daemon/build.gradle.kts` no longer declares `iosArm64()` / `iosSimulatorArm64()`.

### LOW (Code quality / hygiene)

#### ERROR #7: Duplicate AppIcons Object in DesignSystem

  - `core/designsystem/src/commonMain/kotlin/bo/bordadoxdanny/app/core/designsystem/components/icons/AppIcons.kt`

The first one in `icons/AppIcons.kt` is unused. Also, importing `bo.bordadoxdanny.app.core.designsystem.*` in both files is suspicious.

#### ERROR #8: ProfileDao Query Uses Class Name Instead of Table Name
- **Location**: `composeApp/src/commonMain/kotlin/bo/bordadoxdanny/app/features/profile/data/ProfileDao.kt` line 18
- **Error Type**: Logic
- **Root Cause**: Query is `SELECT * FROM ProfileEntity WHERE id = 1` but `ProfileEntity` has no `@Entity(tableName = "...")`, so Room uses `ProfileEntity` as table name. While this works, it's inconsistent with other tables that use snake_case (e.g., `report_summaries`, `cash_entries`). If a future developer adds `tableName = "profiles"`, this query will break silently.
- **Fix Applied**: Add `@Entity(tableName = "profiles")` to `ProfileEntity` and update query to `SELECT * FROM profiles WHERE id = :id`. This makes it consistent with the rest of the codebase.
- **Verification**: Ensure Room schema generation doesn't conflict (version bump may be needed if data already exists, but since it's a new project, version can stay the same).

#### ERROR #9: OrderEntity Uses Clock.System.now() as Default Value
- **Location**: `composeApp/src/commonMain/kotlin/bo/bordadoxdanny/app/features/orders/data/OrderEntity.kt` line 20
- **Error Type**: Logic
- **Root Cause**: `createdAt: Long = Clock.System.now().toEpochMilliseconds()` uses a call expression as a default value. In Kotlin data classes, default values must be compile-time constants or at least evaluable at the site of object creation. While `Clock.System.now()` is not a compile-time constant, Kotlin allows it as a default parameter value in data classes. However, this means each time an `OrderEntity()` is constructed without specifying `createdAt`, it captures a new timestamp. This may be intentional but is worth noting because if you later deserialize from JSON/Room, the default is only used when the value is missing.
- **Fix Applied**: No action needed — this is valid Kotlin and serves the intended purpose. Documented for clarity.

#### ERROR #10: Missing iOS Implementations in ComposeApp Build File
- **Location**: `composeApp/build.gradle.kts`
- **Error Type**: Gradle/Configuration
- **Root Cause**: The `kotlin` block only declares `iosArm64()` and `iosSimulatorArm64()` targets. This is correct. However, the `commonMain.dependencies` includes `libs.koin.compose.viewmodel` which on iOS uses the ViewModel from lifecycle-runtime-compose. The `androidx.lifecycle.viewmodel` dependency is included in `commonMain` but `androidx.lifecycle.viewmodelCompose` is also included. These should be compatible.
- **Fix Applied**: None needed — configuration looks correct.
- **Verification**: Run `./gradlew :composeApp:assemble` for both Android and iOS.
